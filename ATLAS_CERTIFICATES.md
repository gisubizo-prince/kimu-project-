# Certificate API on MongoDB Atlas

## What the current code does

The canonical Express app mounts `routes/certificateRoutes.js` at `/api/certificates`. The staff list request `GET /api/certificates?page=1&limit=10` is implemented and requires an admin or super-admin bearer token. The public routes under `/api/certificates/verify/:token` do not require staff login.

Certificate metadata, verification tokens, status, checksums, audit events, and opaque file keys are stored in MongoDB through Mongoose (`Certificate` and `AuditLog` models). MongoDB creates the collections when records are first written. The PDF bytes themselves are stored in the private directory set by `CERTIFICATE_STORAGE_DIR`, not in Atlas. On a hosted backend that directory must be a persistent private volume shared by all API instances; the provided production template mounts `certificate_files` there. Restarting or replacing an ephemeral backend disk without that volume can make Atlas records point to missing PDFs.

## Meaning of the observed 404

The response text `Route not found: /api/certificates?page=1&limit=10` is generated by the legacy error handler in the old nested backend copy. The current canonical handler deliberately returns `Route not found.` without echoing the URL, and the current app mounts the certificate router. This points to an older backend build or a host configured to run code that predates the certificate route. Creating a MongoDB collection cannot fix an Express 404: the request is rejected before any database query is made.

In the current backend test suite, an unauthenticated request to the management list route returns **401**, and an authorized request exercises listing and pagination. If the hosted route still returns `Route not found`, the host is not serving this backend build/entrypoint.

## Backend host configuration

Deploy the latest repository revision to the backend service using the canonical backend directory `kimu-backend`:

- Install/build: `npm ci`
- Start: `npm start` (runs `node server.js`)
- Runtime: Node.js `>=22.12 <23`
- Set `NODE_ENV=production`, `MONGO_URI`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `CLIENT_URL`, `PUBLIC_APP_URL`, `TRUST_PROXY_HOPS`, and an absolute persistent `CERTIFICATE_STORAGE_DIR` in the host's secret/configuration settings.
- `MONGO_URI` must be an Atlas `mongodb+srv://` URI for the intended database. Give the backend database user access only to the application database (Atlas `readWrite` for that database is needed for normal model writes/index creation). Restrict Atlas Network Access to the backend's documented egress IPs where available; do not expose the URI in frontend configuration or commit it to Git.
- Set the frontend build variable `VITE_API_URL` to the deployed API origin ending in `/api`, then rebuild/redeploy the frontend. It must point at the same backend receiving the request.
- Set `CLIENT_URL` to the frontend's exact HTTPS origin and `PUBLIC_APP_URL` to the HTTPS origin embedded in certificate QR codes.

Do not manually insert a placeholder certificate or edit collection documents. After the correct API build is running, the first authorized certificate registration writes a validated record and audit event to Atlas and stores the uploaded original plus generated printable PDF on the private persistent volume. Use the staff UI/API to create real certificate records.

## Safe post-deployment checks

1. `GET /api/health` should return 200 with `{"success":true,"status":"ready"}` when the API is connected to MongoDB.
2. Without a bearer token, `GET /api/certificates?page=1&limit=10` should return 401, not a route-not-found 404.
3. Sign in with an existing authorized staff account and load the certificate register. An empty register is a successful route response; it does not indicate a missing collection.
4. Register a real test certificate only after selecting a non-production/staging Atlas database. Confirm the metadata and audit event appear in the intended database and both PDF files remain downloadable after a backend restart.
5. Verify public token resolution and the printable PDF URL over HTTPS. Never use a production certificate as a test fixture.

These checks require the actual host and Atlas configuration. They were not run against the hosted service or live Atlas from this workspace. No live Atlas data was inserted or changed here.
